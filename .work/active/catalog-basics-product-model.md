# One plugin, one catalog item

Status: APPROVED after independent Codex/Sol specification critique (identity and last-format lifecycle refinements passed). Acting planner: Codex/Astra. Parent cleanup-essentials remains open. User authorized a top-down audit and implementation of the basic catalog workflow, then clarified that plugin formats are attributes of ONE database entity.

## Audit and outcome

The current database owns plugin tags and evidence through physical format nodes; `PluginProduct.group` is explicitly a presentation grouping. This causes fragile representative-file identity, repeated tag writes, inconsistent grouped search, and date projections tied to current formats. The live catalog has 61 installations representing 30 products: all sizes measured; 21 products have Finder dates; the other 9 lack that metadata on disk. Only one qualified usage record exists. Available native history is Cubase; the other primary hosts are absent here. Never fabricate missing history.

The product is a simple local catalog: browse sounds, search names/tags, edit tags, and sort by tags, Date added, or Last used. The Your Sound inspector contains the selected name, formats, tags, three short values, and relevant actions. Remove Show Details and the diagnostic/history body entirely from that inspector; do not replace it with an always-open wall of text. Existing Scan details and format management can retain useful diagnostics. This user direction supersedes older instructions requiring inspector provenance paragraphs.

## Foundation: durable product identity

1. Introduce an additive, transactional schema migration from v4 with the existing verified pre-migration backup mechanism, also preserving earlier supported upgrade paths. Persist one canonical plugin product record and subordinate installation attributes/relations (format, path, current availability, bytes, physical identity, source identifiers). Physical records remain necessary for reading/removal safety; they are not independent user catalog items.
2. A persisted product ID survives adding/removing/reordering formats, rescans, verified moves, and same-product updates. Reuse verified family/bundle identity rules to associate formats; never merge unrelated vendors or ambiguous same-name products. Existing node membership takes precedence over a newly derived display name. Existing membership applies only to the exact surviving installation node. A replacement/new installation may inherit a product only through one unique product-specific verified identifier or explicit validated cross-format alias; display-name/vendor coincidence alone is insufficient. Zero candidates create a new product; multiple candidates remain unresolved/separate without inheriting tags or dates. Audit the current broad vendor grouping heuristics before using them for durable ownership; preserve supported product-specific alias rules, not a blanket vendor merge. Conflicting identity remains separate, not a silent merge. No speculative fuzzy matching or new identity service.
3. Product metadata has ONE durable owner. Migrate existing explicit format overrides without dropping values: normalized deterministic union per facet; explicit empty overrides still suppress suggestions when no nonempty override exists. Keep legacy sources in backup/archived storage for conflicting historical overrides. New edit/undo/reset acts once on the product, not a fanout to format nodes. Preserve sample/instrument metadata behavior.
4. Migrate and retain existing usage/addition evidence, with installation provenance still bound safely to its physical source. Product Date added is the earliest qualified Finder date observed for the product; removing a format or moving/replacing a file must not make the product newly added. Confirmed addition remains an explicit qualified fallback, never scan/birthtime/installer substitution. Last used is the latest qualified positive event from any member, retained when a format is removed. Do not rewrite or weaken host evidence admission. Product size sums currently installed complete measurements, with honest partial/unavailable state.
5. Catalog snapshots and UI use persisted product identities. Product tags, search keys, dates, sorting, selection, and reopen derive from that same record. A presentation-only cache or another wrapper around independently owned format metadata does not satisfy this task. Installation-specific removal remains explicit and reviewed; removing one format preserves the product and its history. Successful removal of the last installation archives the product from the active catalog while retaining ID, tags and historical dates/evidence. Missing/offline/unobserved files are unavailable, not confirmed removal. A later installation can reactivate an archived product only through the unique verified identifier/alias rule above; ambiguous matches never resurrect it or inherit history. Failed/canceled removal changes neither product availability nor membership. Current format count and size use only the current scope and observed installation state; stale membership from another scope must not contribute current bytes/availability.

## Simple complete workflow

- Remove the inspector disclosure/history UI. Keep Manage formats visible for plugins and Show in Finder for applicable sample/library items. No duplicate path list in the normal plugin inspector. Use short date values without timezone/source suffixes. Missing facts remain honest; concise tooltips/accessibility can explain absence without an essay. Keep current colors, typography, and native controls.
- Add a visible sortable Tags column using the same effective product tags shown in the inspector and searched. Alphabetical normalized tag ordering, stable name/ID ties, untagged items last in either direction. Preserve header-based date sorts and known-first ordering. Do not add a panel of facet controls or new search syntax.
- Search uses the canonical product's displayed name and effective tags together, including terms previously spread over different formats. Multiword queries, case/diacritics, edit/undo/reopen, empty results, and selection must behave consistently. Extend the existing mechanisms; no new search service.
- Apply available Finder Date Added metadata consistently to actual cataloged sample/library files and exact instrument locators, with no invented dates for virtual/shared entities. Dates and ordering must share one projection. Preserve real sample reference recency as explicitly labeled reference information, never relabel project modification as Last used. Library/instrument usage remains unavailable unless an actual qualified source exists.
- Date/tag ordering must help find sounds across the chosen collection: retain normal hierarchical Name browsing; use flat sound results with existing breadcrumb context for cross-collection date/tag sorts where hierarchy would defeat ordering. Preserve identities/selection on returning to Name browsing. Do not duplicate a library container as every instrument's date/use; use actual item data only.
- Keep known historical values while refreshing; show Checking only where a value has never been established. Restore saved data immediately. After normal launch/restore, schedule one background refresh of the selected configured collection through the existing bounded scanner (no overlapping scans, no loop or extra host launch). Preserve tags, selection, offline history and responsiveness. Do not continuously rescan large external libraries or enable new privileges.
- Missing optional standard plugin roots should not mark an otherwise complete inventory as failed. Actual configured-root errors, scan limits and unreadable files remain reported. Existing Scan details gets a concise aggregate coverage statement (known addition/use counts) so missing source data is distinguishable from a failed scan, without adding inspector clutter.
